# 試行の記録: pstack の解説ドキュメントを作る

全4節。読むのに約6分。

**結論**: 4つのスキルは、返信をすぐ待てる会話を前提にしている。非同期のスレッドでは、cog-ask、cog-learn、cog-review の3つが作業を止める。最初に直すのは、返信を待つ間の振る舞いを決めること。

この記録は、読み手が言った「読みにくい」の記録ではない。エージェントがスキルを使って気づいた点の記録。そのため `feedback/log.md` には入れず、この文書に置く。読み手が同じ点を指摘したら、`feedback/log.md` に記録する。

## 試行の条件

| 項目 | 内容 |
|---|---|
| 題材 | pstack の使い方を、開発フェーズと用途ごとに解説するドキュメント |
| 環境 | Claude Code のクラウドのスレッド。読み手は依頼を送った後に席を外していた |
| 使ったスキル | cognizable（会話と `/cognizable doc`）、cog-plan、cog-ask、cog-review。cog-learn は最初のステップだけ |
| 成果物 | Markdown のノート、4層の HTML（`scripts/check.py` を1回で通過） |

## 1. 返信を待つスキルは、非同期のスレッドで作業を止める

cog-ask、cog-learn、cog-review は、1回の出力に1問か1ステップだけを入れ、読み手の返信を待つ。読み手が席を外していると、返信が来るまで作業が止まる。

| 気づいた点 | 起きたこと | 直す案 |
|---|---|---|
| cog-ask に、返信を待つ間の規定がない | 推奨の選択肢で本文を書き進めた。cog-ask の「決定の表を確認するまで実装を始めない」に反した | 取り消せる作業に限り、推奨で仮に進めてよいと書く。仮に進めたことを問いの最後の行に書く |
| 3つのスキルを同時に走らせると、返信の宛先が分からない | cog-review と cog-learn の両方が「次へ」を待つ状態になりかけた。そのため cog-review は全ステップを書き出した | 返信を待つスキルは、同じ会話で1つだけにする、と4つのスキルの共通の決まりに書く |
| cog-ask の問いの形が、ハーネスの決定カードに収まらない | カードは選択肢の名前が40バイト、結果が200バイトまで。背景と推奨の理由を載せる場所がない | ハーネスにカードがあるときの短い形（問い、選択肢、推奨の3つ）を、問いの形の別表として書く |

## 2. 文書の変換で、群化と1画面の判断が書き手に残る

`/cognizable doc` の L1 は4ブロックまで。依頼の関心点は4つで、加えてフェーズごとの使い方の解説があり、5ブロックになった。2つの関心点を1ブロックにまとめて4ブロックにした。

| 気づいた点 | 起きたこと | 直す案 |
|---|---|---|
| 5ブロックを4ブロックにまとめる基準がない | まとめ方を書き手が決めた。根拠は「同じ問い（何をリポジトリに残すか）に答える」だった | `references/transform.md` の「群化する」の手順に、同じ問いに答えるブロックをまとめる、と書く |
| L0 が1画面に収まるかを検査しない | 1280×900 の画面で、L0 の用語表が画面の外に出た。`scripts/check.py` は通った | `scripts/check.py` に、L0 の文字数の上限を足す。上限の値は開始値として決め、記録で調整する |
| L1 の箇条書きは、項目の数だけを数える | ブロック2の箇条書きは4項目だが、各項目が2文あった | 1項目を1文にする、と R5 か `references/transform.md` に書く。検査に句点の数を足す |
| ひな形が完全な HTML 文書になっている | Artifact で公開するには、`<html>` と `<body>` を外した断片が要った。変換を手で行った | `assets/template.html` の近くに、Artifact に公開するときの手順を書く |

## 3. 数と行番号は、書く前に機械で出す

| 気づいた点 | 起きたこと | 直す案 |
|---|---|---|
| 数を数えずに書いた | cog-plan の出力で、pstack のスキルを「60個」と書いた。数え直すと56個だった。送った後に直した | 送信前の確認に「本文の数は、数えるコマンドの出力から書いたか」を足す（R12 の補足） |
| 行番号を手で書いた | cog-review の下書きで、`パス:行番号` が4か所ずれた | cog-review の手順1に、見出しの行番号を `grep -n` で出してから書く、と足す |
| 文書だけの差分の並べ方がない | cog-review の「入口からドメインへ」も「呼ぶ側から呼ばれる側へ」も、文書の差分に当てはまらなかった | 文書の差分は「冒頭の要約、本文の節の順、付属のファイル」の順に並べる、と足す |

## 4. 呼び名とスキルの置き場がそろっていない

| 気づいた点 | 起きたこと | 直す案 |
|---|---|---|
| 読み手は「sharpen」と呼ぶ。スキルの名前は cognizable | pstack にも `/sharpen` がある。pstack の `/sharpen` は、プロンプトを深くして書き直すスキル。依頼の「sharpen を実行」が、どちらを指すかを確かめる必要があった | README の冒頭に、旧名 sharpen と pstack の `/sharpen` は別物だと1行で書く |
| このセッションのスキル一覧に、cognizable 系のスキルがなかった | SKILL.md をリポジトリから読み、手で適用した | 使う環境ごとの置き場（Claude Code のプラグイン、`~/.claude/skills/`）を README の「使い方」に書く |

## 優先する順番

1. 節1の「返信を待つ間の規定」と「返信を待つスキルは1つだけ」。非同期のスレッドで4つのスキルを使うたびに起きる。
2. 節3の「数は数えるコマンドの出力から書く」。誤った数が、読み手の判断の材料になる。
3. 節2の `scripts/check.py` の検査2つ（L0 の分量、箇条書き1項目の文の数）。
4. 節4の README の追記。
