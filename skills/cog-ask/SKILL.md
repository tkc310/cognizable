# cog-ask

設計を決定の木として扱う。読み手が決める問いを、1回に1問ずつ出す。問いが尽きるまで続ける。

問いを1問ずつ出す理由は2つ。1つ目は、複数の問いをまとめて出すと、読み手はすべての問いを保持したまま答えることになるため。2つ目は、推奨回答つきの問いをまとめて出すと、読み手は推奨に「はい」と答えるだけになりやすいため。

## 使い方

```
/cog-ask 設計したい内容
/cog-ask html 設計したい内容
```

設計したい内容が書かれていないときは、直前の会話か、`cog-plan` の出力の「人が決める判断」から読み取る。

## 出力には cognizable を適用する

始める前に、このスキルと同じ置き場にある `cognizable/SKILL.md` を読む。このスキルが出す文は、すべて `cognizable/SKILL.md` のルール R1〜R19 に従って書く。

`cognizable/SKILL.md` を読めないときは、読めないことを1行で読み手に伝える。そのうえで、次の5つを守って続ける。

1. 結論と次の行動を先頭に置く。
2. 読み手が覚えるか比べる項目は、4つまでにする。
3. 指示語を使わず、対象の名前をもう一度書く。
4. 主語と目的語を省略しない。
5. 前提から結論までの推論の段を飛ばさない。

このスキルが終わった後の応答は、`/cognizable` が有効なときだけ cognizable のルールに従う。

## 決定の木の扱い方

- 設計の判断は、木の形につながっている。1つの判断を決めると、その判断に依存する次の判断が現れる。
- 「今出せる問い」は、前提になる判断がすべて決まっている問いだけ。前提が決まっていない問いは、後に回す。
- 読み手が1問に答えるたびに、木を更新する。更新した木から、次に出す問いを選ぶ。
- 今出せる問いが複数あるときは、他の判断に最も多く影響する問いを先に出す。

## 問いにするものと、しないもの

| 種類 | 扱い |
|------|------|
| 読み手の意図、優先順位、好みで決まる判断 | 問いにする |
| コードや資料を調べれば答えが決まる事実 | `cog-ask` が自分で調べる。問いにしない |
| どの選択肢でも結果がほぼ変わらない判断 | `cog-ask` が決めて、決めた内容を最後の表に書く |

事実を調べている間に、調べた結果に依存しない問いがあれば、その問いを先に出してよい。

## 手順

1. 設計したい内容を読み、最初の木を作る。木は読み手に見せない。
2. 最初に、全体を2行で伝える。1行目は、何を決めるための問いか。2行目は、問いのおおよその数。
3. 今出せる問いを1つ選び、下の「問いの形」で出す。
4. 読み手の答えを待つ。答えが来るまで、次の問いを出さない。
5. 答えを受けて木を更新する。答えによって不要になった問いを消し、新しく現れた問いを足す。
6. 手順3〜5を、今出せる問いがなくなるまで繰り返す。
7. 下の「終わりの形」で、決まった内容を出す。

## 問いの形

問いは、毎回次の形で出す。項目の順番と名前を変えない。

```
問い 3（決定済み2件、残り約4問）
招待トークンを、データベースにどの形で保存するか。

背景: 招待トークンは、招待メールのリンクに入る文字列。データベースが漏れた場合に、保存の形で被害が変わる。

選択肢:
A. ハッシュ化して保存する（推奨）。漏れてもトークンを復元できない。
B. そのまま保存する。実装は最も単純。漏れるとトークンをそのまま使われる。
C. 保存しない。署名付きトークンにして、検証だけを行う。失効の管理が別に必要になる。

推奨の理由: 既存のパスワードリセットのトークンが、同じハッシュ化の方式で保存されているため。

答え方: A、B、C のどれかを返信する。選択肢に合うものがなければ、考えを一言で返信する。判断の材料が足りなければ「分からない」と返信する。
```

問いの形の決まりは次のとおり。

- 1行目に、問いの番号、決定済みの件数、残りのおおよその問いの数を書く。
- 問いは、主語と目的語を省略しない1文で書く。
- 背景は2文までにする。背景には、読み手が知らない可能性のある用語の定義を含める。
- 選択肢は4つまでにする。選択肢ごとに、選ぶと何が起きるかを1文で書く。
- 推奨は1つだけにする。推奨の理由は、手元のコードや資料の事実に基づけて書く。
- 選択肢を2つ以上の観点で比べる必要があるときは、選択肢の後に表を置く。
- 推奨できる根拠がないときは、推奨を付けない。推奨を付けない理由を1文で書く。

## 読み手が「分からない」と答えたとき

1. 選択肢の違いを、3文以内で説明し直す。既知の概念との対比を使う。
2. 説明の後に、同じ問いをもう一度出す。
3. 読み手がもう一度「分からない」と答えたら、`/cog-learn` を勧める。問いは未決のまま残し、他の問いに進む。

読み手が推奨を選び続けていても、理由を問い詰めない。読み手が5問続けて推奨を選んだときは、1回だけ、次の1行を問いの前に置く。

```
確認: 推奨が合わないと感じた問いがあれば、問いの番号を返信してほしい。
```

## 終わりの形

今出せる問いがなくなったら、次の順番で出す。

1. 結論: 決まった設計を1〜2文で書く。
2. 決定の表: 列は「問い」「決定」「理由」の3つ。決定が5つ以上あるときは、関連する決定ごとに表を分ける。
3. `cog-ask` が決めたこと: 結果がほぼ変わらないために `cog-ask` が決めた判断を、箇条書きにする。
4. 未決のこと: 読み手が「分からない」と答えた問いを、箇条書きにする。
5. 次の一手: 1つだけ書く。

読み手が決定の表を確認するまで、決定に基づく実装を始めない。

## HTML で出すとき

`/cog-ask html` と頼まれたとき、または読み手が HTML を頼んだときに使う。比較の表や図が多い設計に向く。

1. 今出せる問いを、すべて集める。答えによって変わる問いは、HTML に入れない。
2. `assets/wizard.html` をコピーする。コピーしたファイルの `QUESTIONS` に、集めた問いを書く。`QUESTIONS` の形は、`assets/wizard.html` の中のコメントに書いてある。
3. HTML は、1画面に1問を表示する。HTML は、ローカルサーバーなしで、ファイルを開くだけで動く。
4. 読み手は、最後の画面で「回答をコピー」を押し、コピーした回答を会話に貼る。
5. 貼られた回答で木を更新する。新しく出せる問いが現れたら、会話の中で1問ずつ続けるか、HTML をもう一度作る。

## してはいけないこと

- 2問以上を1回の出力に入れない。
- 調べれば分かる事実を、読み手に聞かない。
- 読み手が答えていない問いを、推奨で確定させない。

## 4つのスキルの流れ

| 順番 | スキル | 役割 |
|------|--------|------|
| 1 | `cog-plan` | 実装の計画を、成果物とプロセスの流れ図にする |
| 2 | `cog-ask` | 設計の問いを、1回に1問ずつ読み手に出す |
| 3 | `cog-learn` | 読み手が詰まった箇所を、約5分のレッスンで教える |
| 4 | `cog-review` | 変更の差分を、読む順番と説明を付けて案内する |

4つのスキルは、単独でも使える。
