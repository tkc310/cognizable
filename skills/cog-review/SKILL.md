# cog-review

変更の差分を、読み手が理解しやすい順番に並べ直して案内する。目的は、読み手が変更を自分で理解して、レビューの判断を下せるようにすること。

`cog-review` は、問題を探す道具ではない。問題を探すレビューは、別のコードレビュー用のスキルで行う。`cog-review` が案内の途中で気づいた問題は、最後に別件としてまとめる。

## 使い方

```
/cog-review 対象
/cog-review html 対象
```

対象は、ブランチ名、PR の番号、コミットの範囲のどれかで指定する。対象が書かれていないときは、現在のブランチと、ブランチの分岐元との差分を対象にする。

## 出力には cognizable を適用する

始める前に、このスキルと同じ置き場にある `cognizable/SKILL.md` を読む。このスキルが出す文は、すべて `cognizable/SKILL.md` のルール R1〜R19 に従って書く。

`cognizable/SKILL.md` を読めないときは、読めないことを1行で読み手に伝える。そのうえで、次の5つを守って続ける。

1. 結論と次の行動を先頭に置く。
2. 読み手が覚えるか比べる項目は、4つまでにする。
3. 指示語を使わず、対象の名前をもう一度書く。
4. 主語と目的語を省略しない。
5. 前提から結論までの推論の段を飛ばさない。

このスキルが終わった後の応答は、`/cognizable` が有効なときだけ cognizable のルールに従う。

## 手順

1. 差分を読む。変更されたファイル、関数、型を洗い出す。
2. 影響箇所を洗い出す。変更された関数や型を使っている箇所を、検索か型の情報で調べる。差分に含まれない影響箇所も含める。
3. 洗い出した箇所を、入口からドメインの方向へ並べる。入口は、画面、API のエンドポイント、コマンド、ジョブの起動点。ドメインは、業務のルールを持つコードと、データの保存。
4. 並べた箇所を、3〜4ステップに束ねる。1ステップは、1つのまとまった役割にする。
5. 最初に、全体の地図を出す。読み手の返信を待つ。
6. ステップを1つ出す。読み手の返信を待つ。
7. 手順6を、最後のステップまで繰り返す。
8. 下の「終わりの形」で締める。

1回の出力に入れるステップは1つだけにする。

## 並べる順番の決まり

- 読み手が変更を「利用者の操作から順に」たどれる順番にする。差分のファイル名の順にしない。
- 入口からドメインへの順番が当てはまらない変更では、「呼ぶ側から呼ばれる側へ」の順にする。
- テストの変更は、テストが確かめている実装と同じステップに入れる。
- 名前の変更、整形、自動生成されたファイルは、1つのステップにまとめて最後に置く。まとめたステップには「読み飛ばしてよい」と書く。

## 全体の地図の形

次の順番で書く。

1. 結論: 変更全体が何をするかを1〜2文で書く。
2. 規模: 変更されたファイルの数と、ステップの数を書く。読むのにかかる時間の目安を書く。
3. 地図: ステップの見出しを、番号付きで並べる。ステップ間のつながりを、矢印か接続語で示す。
4. 用語: 変更の中で繰り返し出る独自の語を、3〜5語。1語につき1行で定義する。
5. 次の一手: 「ステップ1に進むなら『次へ』と返信する」と書く。

## ステップの形

ステップは、毎回次の順番で書く。

1. 位置: 「ステップ 2（全4ステップ）」の形で書く。
2. 見出し: ステップで何が変わったかを、文で書く。
3. 何がなぜ変わったか: 短い段落で書く。1段落は3文まで。変更の前と後を、両方書く。
4. 前後とのつながり: 前のステップから何を受け取り、次のステップへ何を渡すかを、1〜2文で書く。前のステップの内容は、もう一度書く。
5. 読む場所: `パス:行番号` の一覧。一覧の項目ごとに、その場所で何が行われるかを書く。項目は5つまでにする。
6. 確認点: 1〜3個。下の「確認点の決まり」に従う。
7. 次の一手: 「次のステップに進むなら『次へ』と返信する」と書く。

## 確認点の決まり

確認点は、読み手がコードを見て自分で答える問い。`cog-review` は、確認点の答えを先に書かない。

- 確認点は、変更の正しさに関わる箇所に付ける。例: 処理の順番、エラーのときの振る舞い、権限の確認、データの整合性。
- 確認点は、「はい」か「いいえ」では答えられない問いにする。
- 確認点には、見る場所を `パス:行番号` で添える。

確認点の例: 「招待の保存と、メール送信のジョブの投入は、どの順番で行われているか。見る場所: `app/services/invite.ts:58`」

読み手が確認点の答えを返信したら、答えが合っているかを1行で返す。読み手が「答えを教えて」と返信したら、答えと根拠を書く。

## 終わりの形

最後のステップの後に、次の順番で書く。

1. 結果: 変更全体を1〜2文でもう一度書く。
2. 確認点のまとめ: 読み手が答えた確認点と、答えていない確認点の数を書く。
3. 別件: 案内の途中で `cog-review` が気づいた問題を、ここで初めて書く。問題ごとに、場所（`パス:行番号`）、何が問題か、なぜ問題かを書く。問題が5つ以上あるときは、重要な順に並べて4つずつに分ける。問題がなければ「気づいた問題はない」と書く。
4. 次の一手: 1つだけ書く。

別件は、問題を網羅した一覧ではない。別件の先頭に、次の1行を置く。

```
別件は、案内の途中で気づいた問題だけ。問題を網羅して探すレビューは、別に行う必要がある。
```

## HTML で出すとき

`/cog-review html` と頼まれたとき、または読み手が HTML を頼んだときに使う。`cognizable/assets/template.html` を元に、4層の HTML にする。

| 層 | 置くもの |
|----|----------|
| L0 | 全体の地図（結論、規模、地図、用語） |
| L1 | ステップごとの見出し、何がなぜ変わったか、前後とのつながり |
| L2 | 読む場所の一覧、確認点 |
| L3 | コードの行へのリンク |

別件は、最後の L1 のブロックの後に、独立した節として置く。

## してはいけないこと

- 案内の途中で、問題の指摘を挟まない。
- 確認点の答えを、読み手が考える前に書かない。
- 差分を読まずに、コミットメッセージや PR の説明だけから案内を作らない。

## 4つのスキルの流れ

| 順番 | スキル | 役割 |
|------|--------|------|
| 1 | `cog-plan` | 実装の計画を、成果物とプロセスの流れ図にする |
| 2 | `cog-ask` | 設計の問いを、1回に1問ずつ読み手に出す |
| 3 | `cog-learn` | 読み手が詰まった箇所を、約5分のレッスンで教える |
| 4 | `cog-review` | 変更の差分を、読む順番と説明を付けて案内する |

4つのスキルは、単独でも使える。
