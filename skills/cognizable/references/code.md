# ソースコードの変換

`/cognizable doc 対象` の対象がソースコードのときに使う。4層の構造と変換の手順は `references/transform.md` に従う。このファイルは、各層に置くものだけを決める。

## 4層に置くもの

| 層 | 置くもの | 図の型 |
|----|----------|--------|
| L0 | システムの目的を1〜2文。外部とのつながり。最初に読むファイルを1つ | 一方向の流れ図。3〜4ブロック |
| L1 | モジュールごとの責務。モジュール間の依存。入口となるファイル | 浅い階層図か流れ図。7〜9ノード |
| L2 | 主要な処理の流れ。中核の関数とファイルパスの一覧。設定値の一覧 | 処理ごとに一方向の流れ図を1枚 |
| L3 | コードの行へのリンク | なし |

## L0: 目的と外部とのつながり

1. 目的: システムが誰のために何をするかを書く。実装の技術名から始めない。
2. 外部とのつながり: 利用者、外部サービス、データの保存先を、3〜4ブロックの流れ図にする。
3. 最初に読むファイル: 入口を1つだけ示す。パスで書く。
4. 主要な用語: コード内で繰り返し出る独自の語を3〜5語。1行で定義する。

## L1: モジュールと依存

L1 のブロックは、モジュールか責務の単位で3〜4個にする。ディレクトリの数が多いときは、責務でまとめ直す。

ブロックごとに次の3つを書く。

1. 見出し: モジュールが何を担うかを文で書く。例: 「`auth/` はトークンの発行と検証だけを担う」
2. 依存: どのモジュールを呼び、どのモジュールから呼ばれるか。
3. 入口: モジュールの中で最初に読むファイルと関数。

## L2: 処理の流れと手がかり

1. 処理の流れ: 主要な処理を1つ選び、呼び出しの順を流れ図にする。1枚の図に1つの処理だけを入れる。分岐が3つ以上あるときは、正常系だけを図にする。例外系は表にする。
2. 手がかりの一覧: 中核の関数名、型名、ファイルパスを表にする。列は「名前」「場所」「役割」の3つ。
3. 設定値: 環境変数や設定ファイルの項目を表にする。列は「名前」「既定値」「変えると何が起きるか」の3つ。

## L3: コードの行

- リンクは `パス:行番号` の形で書く。
- リンクには、リンク先で何が行われるかを添える。例: 「`src/auth.ts:42` トークンの期限を検証する」
- コードを長く写さない。写すときは、説明に必要な10行以内にする。

## 両方向にたどれるようにする

コードを読む人は、全体からの理解と細部からの理解を行き来する。次の2つを必ず置く。

- 下る道: L0 の地図の各ブロックから、L1 の見出しへのリンク。
- 戻る道: L1、L2、L3 のどの位置からも、L0 の地図へのリンク。

## 変換のときに調べること

1. 入口を見つける。`main`、ルーティングの定義、コマンドの登録を探す。
2. 依存を数える。モジュール間の import を集計し、呼ばれる回数が多いモジュールを中核とみなす。
3. 主要な処理を1つ選ぶ。利用者の操作を1つ決め、入口から保存先までをたどる。
4. 推測で書かない。コードで確かめられなかった箇所には「未確認」と書く。
